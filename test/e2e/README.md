# PRD acceptance suite

`prd-6.12.spec.ts` has one black-box test for each document scenario in PRD §6.12; `cockpit-engine.spec.ts` and `cockpit-drafts.spec.ts` cover the engine scenarios. The tests launch the built Electron main process and inspect only visible UI, `window.strata.getState()`, document/buffer files, and what the fake engine received. Agents are T3 threads served by `cockpit-engine-harness.ts` (HTTP snapshots plus a real WebSocket subscription server); a test attaches a thread by sending the document to it and drives agent actions by posting an assistant message with a strata block through `postAssistant` (helpers in `cockpit-agent.ts`). A delivery is a `thread.turn.start` command whose uploaded attachment the harness keeps by id.

Each test gets separate `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, and `XDG_RUNTIME_DIR` paths in its own temporary directory outside the repository — deliberately not under Playwright's output directory, which Playwright deletes at the start of every run and would yank a running app's store out from under a concurrent run. It never opens or changes the corpus originals or the owner's normal StrataMD store.

The standard suite runs on Linux and macOS. Windows CI runs explicit document and managed-engine checks; see `docs/platforms/windows.md`. On Linux, run it under `xvfb-run` so app windows do not steal focus; on macOS it runs directly — no display layer exists or is needed. The harness handles the platform differences: it passes X11/ozone launch arguments only on Linux, sets `STRATAMD_USER_DATA` so each scenario gets its own Electron profile and single-instance lock (Electron only derives these from `XDG_CONFIG_HOME` on Linux), and exports key helpers (`primaryKey`, `documentStartKey`/`documentEndKey`, `lineStartKey`/`lineEndKey`, `selectToLineEndKey`) that map to Ctrl/Home/End on Linux and the Command-key equivalents on a Mac. Specs use the helpers instead of literal `Control+...` or `Home`/`End` presses, which do not move the caret on macOS.

The UI contract used by the suite is semantic:

- source textbox: `Source editor`
- visual contenteditable: `Document editor`
- dialogs named by their visible headings
- real buttons for Save, Send, Start thread, Keep, Revert, Accept, close-tab, recovery, and conflict actions
- per-item checkboxes under the heading `Changes not made by you`

These names follow the PRD and design handoff and make the same controls available to keyboard and assistive-technology users.

## Scheduling

`playwright.config.ts` splits the suite into three projects that run in one invocation:

- `ordinary` runs every untagged test, in parallel at the individual-test level: six workers on a Linux workstation, two on Linux CI.
- `managed` runs stock-runtime checks one at a time when a bundle is supplied.
- `clipboard` runs the tests tagged `@clipboard` one at a time on a single worker.

Managed mode also runs its Vitest integration files on one worker. Each starts native servers and copies the stock runtime. Windows run 34427552364 showed concurrent copies taking 49 seconds initially and up to 199 seconds after timed-out attempts overlapped retries. The managed cap covers this disk-heavy preparation as well as the Electron checks; ordinary unit tests and desktop workers retain their existing scheduling.

Windows verification commands start in a native kill-on-close job before they can spawn children. Command exit and cancellation close that job, including detached descendants that retain output pipes. `test/unit/windows-verification-process.test.ts` checks both paths and preserves an unrelated process.

On macOS and Windows the global worker count is one, so the projects run one after the other: a Mac has one desktop, one focus, and one clipboard, and two Electron apps on it would compete for both.

### One X display per worker

Every launch of the app ends with the main process focusing its window. On one X display with no window manager that takes focus from every other Electron window; the top bar and path context menus close on `blur`, so a test with a menu open loses it the moment another worker's app appears. That, not pointer clamping, was behind the "pointer and hover" flakes that led to the suite being run serially on 2026-09-03.

`test/e2e/display.ts` is the Playwright global setup. On Linux with more than one worker it starts one `Xvfb` per worker slot at 2560x1600 (larger than any window a spec asks for), publishes the display list in `STRATAMD_E2E_DISPLAYS`, and stops the servers at teardown. `Scenario.create` sets `DISPLAY` for its app from that list by the worker's `parallelIndex`, so at most one app window exists on any display. The outer `xvfb-run -a` in the gate command stays; it keeps the command shape and costs one idle server.

Setup never falls back to the shared display: if Xvfb cannot start, the run fails naming the serial command. A supplied `STRATAMD_E2E_DISPLAYS` must list at least one display per worker, and the harness refuses a multi-worker run without a list. Because X selections belong to a display, the isolation also separates the clipboard on Linux; the `@clipboard` tag stays because macOS still shares one.

### Clipboard tag

Every Electron app on the display shares one operating-system clipboard; separate profiles do not isolate it. Any test that reads or writes the native clipboard carries the tag, including Electron's `clipboard` module, Ctrl/Command+C, X, or V, the editor's Copy, Cut, and Paste menu items, and Copy full path. Put it next to the title:

```ts
test('explorer tabs copy full paths', { tag: '@clipboard' }, async ({}, testInfo) => {
```

`test/unit/e2e-clipboard-tags.test.ts` fails when a test touches the clipboard without the tag, or carries the tag without touching it. The `@` in the config's grep pattern is load-bearing: Playwright matches the project name too, so a bare `clipboard` pattern would select every test in that project.

### Worker counts and what "serial" means

The total worker count is the ordinary count plus one, so the clipboard project keeps moving beside the ordinary one. `STRATAMD_E2E_WORKERS=<positive integer>` changes the ordinary count for measurements or unusual machines; it is not a serial run, because the clipboard worker still runs beside it. `--workers 1` on the command line caps the whole run and is the serial pass; it keeps the caller's display and needs no isolation. Do not raise a test timeout to absorb contention, and do not lower the worker count; six ordinary workers is fixed. A run that times out across unrelated specs is sharing the box with another suite run or has a defective test, and either gets fixed at its cause.

Screenshot baselines keep their project-free names (`<name>-linux.png`) through an explicit `snapshotPathTemplate`, so `--update-snapshots` writes the same files as before.

## Writing a spec that holds up

Every flake traced on 2026-09-05 had a mechanism, and they fell into three kinds. Write against all three.

- **Stale closures behind window listeners.** `App.tsx` registers its keydown handler in an effect whose dependencies include the view. After a state change React commits the DOM first and re-registers the listener in a passive effect later, so a key that lands in between runs the previous closure: tab cycling stopped on the tab that was already active, and the source toggle flipped back to the old mode. A spec that presses a shortcut right after asserting the result of the last one is the exact shape that finds this. The product reads such state through refs kept current in `useLayoutEffect`; if a new shortcut misbehaves only under load, look there first.
- **Reading a layout that is still settling.** The history keeps the reading position stable from a `ResizeObserver` when content above the anchored row grows, which fires a frame after the growth. A baseline read in that frame is off by exactly the growth (34 px in the case that failed). Read a position twice across two animation frames and accept it only when it holds; `conversation-comments.spec.ts` shows the shape. Never replace this with a sleep.
- **Hangs that hide inside a budget.** A launch that never comes up or a close the app declines used to run out a two-minute budget in silence. Budgets stay at one minute or under and the harness bounds every close at five seconds, verifies the process exited, and kills it otherwise, so a hang costs seconds and leaves a trace.

Shared setup helpers wait for their result: `selectNavigationTab` waits for the selected tab and visible panel after the reading-state IPC update; `openThread` waits for the requested conversation to be visible after delayed navigation. Use these helpers before reading coordinates or acting on the opened conversation. An upload completing does not mean its turn was dispatched; assert the command separately before posting a fake reply.

The preview specs (`preview-window.spec.ts`) drive real pages through the fake engine's preview automation stream (`startEngine({ previewAutomation: true })`, then `engine.automation(threadId, operation, input)`), and they need one probe the product does not expose: an owner's click landing inside a page is a native input event on a main-process view, which Playwright cannot reach from the renderer. With `STRATAMD_PREVIEW_PROBE=1` the preload exposes `strataPreviewProbe.humanInput(tabId, point)`, which sends that input through the same path an owner's click takes. The harness sets the variable; the probe channel refuses without it. The fake dev server for those pages is `test/e2e/preview-page.ts`.

Rules the unit tests enforce: `test/unit/e2e-timing-rules.test.ts` fails on a fixed sleep beyond the per-file allowance and on a budget above one minute; `test/unit/e2e-clipboard-tags.test.ts` keeps the clipboard tag honest. When you remove a sleep, lower the allowance in the same change.

## Verification gate

Use `node scripts/verify.mjs` from the repository root. The command stages stable inputs, coordinates heavy runs across worktrees, and retains each invocation's evidence. Call local binaries directly when diagnosing a runner problem; checkout-local pnpm scripts may purge installed dependencies.

| Situation | Required checks |
|---|---|
| Iteration | Focused relevant unit/integration files and explicit Electron specs; typecheck TypeScript changes and rebuild product changes before Electron |
| Finished code change | One full gate on the final candidate: TypeScript, all default unit/integration tests, build, all default Electron projects |
| Deterministic failure | Preserve evidence, diagnose and fix, run affected checks, then a clean full gate |
| Intermittent failure | Target explicit files/lines and repeat to investigate a named mechanism; record attempts and failures |
| Routine shell or styling edit | Relevant interaction/visual checks and the ordinary final gate |
| Scheduling, display isolation, launch/shutdown, concurrency-sensitive harness | Focused isolation checks, ordinary gate, and one full stress pass |
| Integration | Reuse matching successful evidence; integration edits require relevant checks and a full gate |

An unexplained intermittent failure prevents clean signoff of the affected candidate. Known flakes are evidence, not exemptions. Passing repeats alone do not establish a fix. Inspect competing processes and resource pressure when unrelated tests time out together. Keep local retries at zero and ordinary workstation workers at six. Stress uses eight ordinary workers with `--repeat-each 2`, preserving managed/clipboard caps; macOS remains serial. Never increase timeouts to absorb contention. Scheduled CI supplies recurring stress coverage and retains evidence for triage.

Measure command invocation through cleanup and task verification from the first invocation through final reporting, including queues, repeats, diagnosis, and gaps. Build time belongs in the reported total. Workstation targets are under one minute for focused feedback and under four minutes for routine final verification. They remain provisional until ten routine tasks have been observed; report their median and slowest totals separately from stress and package work.

### Commands and evidence

```sh
node scripts/verify.mjs focused --task my-change --unit test/unit/editor-undo.test.ts --e2e test/e2e/undo-redo.spec.ts
node scripts/verify.mjs full --task my-change
node scripts/verify.mjs stress --task my-change --finish-task
node scripts/verify.mjs full --task my-change --reuse --finish-task
```

Use one task name across retries and diagnosis. `--finish-task` records when you have reached the final verification result. Focused repetitions require `--repeat N --reason "suspected mechanism"` and explicit Electron file/line selectors. A focused result cannot satisfy a full gate. Stress changes only the ordinary project count and repetitions; managed and clipboard projects retain their caps.

The shared lock lives in `~/.cache/stratamd-verification/heavy-run.lock`. Waiters print its owner, requested mode, and queue time. Cancellation terminates the owned command process group before releasing the lock. SIGKILL or machine death can leave an abandoned lock. Inspect its `owner.json`, PID and remaining process group before manually removing it. Never terminate an unknown process to obtain the lock. Direct ad hoc test commands cannot participate in this cooperative lock; all heavy test runs use the runner.

Every invocation starts a unique directory under `~/.cache/stratamd-verification/runs/`. `STRATAMD_VERIFY_HOME` relocates evidence, never the machine lock. `report.json` records inputs, coverage, skips, attempts, retries, versions and timings; `summary.txt` gives the result. `tasks/<name>.json` includes command time and gaps across invocations. Traces, screenshots and logs remain in the run directory after later runs. Candidate dependencies are copied without hardlinks and removed after cleanup; staged source and build output remain with the evidence.

Tracked files and relevant untracked files enter the fingerprint, including test fixtures, configuration and the native module. Generated caches are excluded. Source and installed dependencies are verified before/after copying; running tests cannot read a concurrently rebuilt checkout. Successful reuse requires identical full input identity, environment and mode/selection coverage. HEAD is recorded for provenance but isn't the reuse key. Failed, interrupted, retried/flaky, incomplete and contaminated results cannot be reused. A budget miss requires diagnosis, not fewer workers, longer timeouts or retries.

The Electron timing boundaries are invocation to first test, first test to last test, and last test to process close. These include display setup and teardown. Per-attempt times and skip names come from the test reports. Collect ten completed routine task records before claiming the provisional budgets are met; retain slow and failed invocations as part of their task. Stress and packaging remain visible in total elapsed time and are compared separately.

### Runtime coverage and CI

```sh
node scripts/verify.mjs managed --task recovery-change
node scripts/verify.mjs packaged --task package-change --finish-task
```

The default full gate runs the standard local selection. Its managed-runtime and packaged tests can skip; the report lists them individually. Changes to the bundled engine, pairing, recovery or native runtime require `managed`, which prepares the pinned stock bundle and runs managed integration and Electron tests. Packaging/CLI installation changes require `packaged`, which prepares and tests the host package. These modes never reuse external build results implicitly. Linux package tests need Xvfb; use `xvfb-run -a node scripts/verify.mjs packaged ...` on a headless host. Native platform behavior must be verified on its host, including the serial macOS gate and package job.

`check.yml` runs the ordinary, managed and packaged checks on Linux and macOS. Its weekly schedule and manual dispatch also run a full double stress pass. Linux CI has two ordinary workers, plus the separate single-worker projects. macOS has one total worker. The workstation stress count remains eight ordinary workers. Existing CI retry counts are one for Vitest and two for Playwright; reports list retried outcomes and the runner refuses a clean result when tests needed retries. Local retries remain zero.

CI streams each verification child's output while retaining the same stage log. Electron runs stop after three final test failures, without changing retries, and the verification runner terminates the owned process tree when Playwright emits no suite or test event for two minutes. Console noise does not reset that watchdog. The progress record remains with the run evidence and names the last event and test.

Every CI outcome retains run records and artifacts for 14 days. On a scheduled failure, the maintainer downloads that record, adds a Known flakes entry with the run URL and failing attempt count, diagnoses the named mechanism with focused checks, and links the repair and corrected evidence before closing the incident. A passing next schedule does not close it. The failed workflow remains the open triage signal; no automatic local stress obligation is added to unrelated changes.


The [implementation audit](verification-audit.md) records the measured baseline, retained coverage and controlled runner/failure proofs. `node scripts/verify-history.mjs` reports the first-ten-task observation count and median/slowest completed task times. Managed mode accepts `--bundle /absolute/path` to copy a prepared stock bundle into its candidate; its contents join the input identity. Otherwise the command prepares the pinned bundle itself. Fonts and native operating-system behavior still require their platform's CI job.

Electron page tracing starts in `Scenario.launch`, including context snapshots and screenshots. Each launch gets its own trace.
